# Module Pipeline — transpilation, resolution, optimization & bundling

How a line of TypeScript in a `packages/*` source file becomes (a) a live module in a
dev server, and (b) a minified, code-split chunk in a production PWA. This is the
"how it actually works" companion to
[LOCAL_PACKAGE_DEVELOPMENT.md](./LOCAL_PACKAGE_DEVELOPMENT.md) (which is the "how do I
use it" guide).

There are **two repos** in play and they consume packages differently:

| Repo | Role | How it gets the packages |
|---|---|---|
| `dash-frontend-core` | develops the **`dash-*`** framework packages | workspace **source** (this repo) |
| `dash-frontend-refactored` | the **apps** (dash-app/mall/system/web) | `dash-*` from **Verdaccio (dist)** + its own `kt-*` from workspace **source** |

The same packages therefore travel through the pipeline twice — once as a published
artifact, once as live source. The sections below follow the whole path.

---

## 1. Stage 1 — package compilation (tsup → esbuild)

Each publishable package is compiled by [tsup](https://tsup.egoist.dev/) (a thin wrapper
around **esbuild**). Two shapes exist, generated by
[`scripts/mirror-packages.mjs`](../scripts/mirror-packages.mjs):

### "Mirror" packages (most `dash-*`, the `kt-*`)
```ts
// packages/<pkg>/tsup.config.ts
defineConfig({
  entry: ['src/**/*.ts', 'src/**/*.tsx', '!src/**/*.test.*'],
  format: ['esm'],
  bundle: false,        // ← transpile each file individually
  dts: false,           // ← no .d.ts (types come from src, see §3)
  clean: true,
  esbuildOptions(o) {
    o.loader = { ...o.loader, '.less': 'empty' }; // ignore LESS imports here
    o.jsx = 'automatic';                          // react/jsx-runtime, no React import needed
    o.jsxImportSource = 'react';
  },
})
```

`bundle: false` is the key decision: esbuild **transpiles each source file in place**
instead of rolling everything into one file. So `dist/` mirrors `src/` 1-for-1
(`src/contexts/auth/X.tsx` → `dist/contexts/auth/X.js`). This is what makes **deep
imports** (`dash-admin/contexts/auth/X`) possible against a published package, and what
lets a consumer's bundler tree-shake at file granularity.

Consequences of `bundle:false`:
- **Imports are preserved, not inlined.** `import {x} from 'dash-utils'` stays in the
  output; the consumer's bundler resolves it. (So a package's own runtime deps must be
  declared — an undeclared import that only worked via workspace hoisting will break a
  registry consumer.)
- **No asset handling.** esbuild doesn't follow/emit `.less`/images in this mode — that's
  why the asset packages use the other shape.
- **Automatic JSX runtime** (`o.jsx='automatic'`) emits `import {jsx} from
  "react/jsx-runtime"` instead of `React.createElement`, so a source file that uses JSX
  **without importing React** still runs. (Classic transform here would crash with
  `React is not defined`.)

### "Single-bundled" packages (`dash-styles`, `dash-modal`, `dash-icons`, `dash-auth`, `dash-boilerplate`, `dash-info`, `dash-interfaces`)
One bundled entry (`entry: ['src/index.ts']`, `format: ['esm','cjs']`, `dts: true`).
These either ship **assets** (LESS/MP3/SVG that esbuild must inline/emit) or are small
leaf libs. `"type": "module"` ensures `dist/index.js` is real **ESM** (and
`dist/index.cjs` is CJS). Getting this wrong — publishing a CJS `index.js` — is what
produces `does not provide an export named X` in an ESM consumer.

### esbuild's job in both cases
- **Strip types** (TypeScript → JavaScript). esbuild does *not* type-check; it erases
  types syntactically. Type safety is a separate `tsc --noEmit` pass.
- **Lower syntax** to the `target` (es2020): class fields, optional chaining, etc.
- **Transform JSX** via the automatic runtime.

## 2. Stage 2 — publishing to the registry (Verdaccio)

`pnpm publish` uploads `dist/` (+ `src/` for type resolution, see §3) to Verdaccio.
Crucially, `pnpm` rewrites `workspace:*` deps to real versions at publish time, so the
published `package.json` is registry-installable. Versioning rules and the
bump→build→publish loop are documented in
[LOCAL_PACKAGE_DEVELOPMENT.md §8](./LOCAL_PACKAGE_DEVELOPMENT.md#8-publishing--re-publishing-to-verdaccio-versioning).

## 3. The resolution model — runtime vs types (two targets)

This is the single most important idea. Each package's `package.json` points **runtime**
and **type-checking** at *different* places:

```jsonc
{
  "main": "dist/index.js",
  "exports": {                       // ← RUNTIME (Vite/Rollup/Node)
    ".": "./dist/index.js",
    "./*": "./dist/*.js",            //   clean deep import  pkg/foo  → dist/foo.js
    "./src/*": "./dist/*.js"         //   compat deep import pkg/src/foo → dist/foo.js
  },
  "types": "./src/index.tsx",        // ← TYPES (tsc/IDE)
  "typesVersions": { "*": { "*": ["src/*", "src/*/index"] } },
  "files": ["dist", "src"]           // ship both
}
```

- **Runtime** uses the `exports` field → `dist/**` (the built JS).
- **Types** use `typesVersions` → `src/**` (the original `.tsx`, full fidelity, no
  `.d.ts` generation needed). This works because the apps use
  `"moduleResolution": "node"`, which **ignores `exports` for type-checking** and consults
  `types` + `typesVersions` instead.

Why split them? Generating `.d.ts` for these packages is fragile (cross-package
`dist/*.js` resolution + pre-existing type errors), so `dts:false` + "source-as-types"
sidesteps it. Runtime still resolves to the built `dist`, so *what you run is what you
publish*.

> **String exports**, not condition objects. `".": "./dist/index.js"` matches **every**
> condition (`import`, `require`, `default`). An object with only `{ "import": ... }`
> breaks CJS `require()` consumers (`No known conditions for '.'`).

## 4. Stage 3 — how an app consumes a package

Two mechanisms, chosen per package:

### a) Registry packages (the `dash-*` in the apps repo) → **built `dist`**
Installed from Verdaccio into `node_modules`. Vite resolves `dash-utils/foo` via the
`exports` map → `node_modules/dash-utils/dist/foo.js`. Types resolve via `typesVersions`
→ `node_modules/dash-utils/src/foo.tsx`.

### b) Workspace packages (the `kt-*` in the apps repo, all packages in core) → **source**
A dev-only **Vite alias** routes the bare package name to its `src`, so Vite serves the
TypeScript source directly (instant HMR, and Vite *scans* the source so its transitive
deps get optimized). The alias strips an optional `/src` so both import forms work:

```ts
// apps/<app>/vite.config.mts  → resolve.alias (array form, dev only)
...["kt-ecommerce","kt-pages","kt-utils","kt-cashcount","kt-kiosk"].map((n) => ({
  find: new RegExp(`^${n}(?:/src)?(/.*)?$`),
  replacement: path.resolve(currentPath, `../../packages/${n}/src$1`),
}))
```

> This is "Workflow B". In `dash-frontend-core`, the **same** alias mechanism makes
> `dash-system` consume *all* `dash-*` packages from source. The rule of thumb:
> **a package you develop locally → consume its source; a package you depend on as a
> published artifact → consume its `dist`.**

## 5. Stage 4 — Vite **dev** pipeline

Two cooperating halves:

### Dependency pre-bundling (esbuild) — `optimizeDeps`
On startup Vite scans the app's import graph and **pre-bundles `node_modules` deps** with
esbuild into `node_modules/.vite/deps/`. This does two things:
1. Converts **CJS → ESM** so the browser (ESM-only) can `import` them, and **flattens**
   many small files into few requests.
2. Caches the result (keyed by a hash) so it's done once.

The catch that bit us repeatedly: a **CJS dependency that the scanner doesn't discover
up-front** (it's transitive behind a registry `dist` package, or a sub-dep like a dayjs
plugin) gets optimized **ad-hoc without interop**, and the browser then fails with
`does not provide an export named 'default'/'X'`. Fix = name it in `optimizeDeps.include`
so Vite pre-bundles it properly:

```ts
optimizeDeps: {
  include: [
    "react", "react-dom", "react-router-dom", "@mui/material", /* … */
    "react-is", "is-mobile",                 // CJS leaf utils
    "@ant-design/icons", "@ant-design/icons-svg", "antd",  // antd ecosystem
    "dayjs/plugin/isBetween", "dayjs/plugin/weekOfYear",   // each plugin used
  ],
  exclude: ["dash-admin", "dash-auto-admin", "dash-admin-state"], // served raw
}
```

After changing the list, `rm -rf apps/*/node_modules/.vite` to force re-optimization.

### On-demand transform (esbuild) — app + workspace source
App code and aliased workspace `src` are **not** pre-bundled — Vite transforms each module
**on request** with esbuild (strip types, JSX) and serves it over native ESM. Edits
trigger **HMR** / React Fast Refresh. This is why dev shows a huge module count and large
*unminified* transfer (~tens of MB): every module is a separate, unminified request with
sourcemaps. **Dev size is not production size.**

---

## 6. Stage 5 — Vite **production** pipeline (Rollup)

`vite build` switches engines to **Rollup** for the app code (esbuild only minifies):

1. **Bundle + tree-shake.** Rollup walks the graph from `index.html` → `main.tsx`, drops
   unreferenced exports (so file-granular `dist/` + named deep imports tree-shake well).
2. **Code-split.** Every `React.lazy(() => import(...))` and dynamic `import()` becomes its
   own chunk. Plus explicit `build.rollupOptions.output.manualChunks` groups vendors
   (`vendor-react`, `vendor-react-admin`, `vendor-mui`, `vendor-utils`, `vendor-heavy`, …).
3. **Minify** with esbuild; **hash** filenames for cache-busting; emit `assets/` (fonts,
   images, the compiled CSS).

The result for these apps (gzip): entry `main` ≈ 38 kB, `vendor-react` ≈ 59 kB, and the
heavy stuff in **separate, lazily-loaded** chunks (`vendor-react-admin` ≈ 282 kB,
`systemResources` ≈ 121 kB, antd inside the e-commerce chunks). See §8.

## 7. The CSS / LESS pipeline

LESS is compiled by Vite's CSS pipeline, **not** by tsup (package builds treat `.less`
imports as `empty`). Each app prepends shared variables via `additionalData`, resolving
the published `dash-styles` source through an alias (since `packages/` isn't present in
the apps repo):

```ts
css: { preprocessorOptions: { less: {
  javascriptEnabled: true,
  additionalData: `
    @import "@dash-styles-src/dash-variables.less";       // node_modules/dash-styles/src
    @import '@app/dash-variables.less';                    // app overrides
    @import "@dash-styles-src/dash-css-transformer.less";  // emits CSS custom properties
  `,
}}}
// resolve.alias:  "@dash-styles-src" → node_modules/dash-styles/src
```

`dash-css-transformer.less` turns LESS variables into **CSS custom properties** at compile
time; runtime layout then reads them via `getCssVariableNumber(...)`. App-level
`dash-variables.less` overrides the package defaults because it's imported *after* them.

## 8. Initial-load strategy (PWA)

The critical path is deliberately tiny. `main.tsx` statically imports only **React +
react-dom + `dash-boilerplate`** (a light shell) and renders a splash, then:

```
main.tsx ──lazy──▶ DashAppComponent (Redux + bootstrap)
                       └─▶ KitchnTabsWebBootstrap  (reads auth state)
                              ├─lazy─▶ PrivateAppLoader  → react-admin  (only if authed)
                              └─lazy─▶ PublicAppLoader   → login        (if not authed)
```

So **react-admin (≈282 kB gzip) never loads on the login screen** — first paint is
≈110 kB gzip (`main` + `vendor-react`). Heavy features (`react-admin`, `antd` via
`kt-ecommerce`, charts, fullcalendar, color-thief) live in lazy route chunks and stream in
only when their route is hit.

Levers to shrink further: tree-shake `lodash` (`import x from 'lodash/x'`), audit the
global LESS (the admin CSS is sizable), and — a larger project — replace antd in
`kt-ecommerce` with MUI to drop the second component library.

## 9. End-to-end summary

```
              dash-frontend-core                         dash-frontend-refactored
              ───────────────────                        ──────────────────────────────
 src/*.tsx ──tsup/esbuild──▶ dist/*.js  ──pnpm publish──▶ Verdaccio ──install──▶ node_modules/<pkg>/dist
   │  (bundle:false, ESM,                                                              │  (runtime, via exports)
   │   automatic JSX, types→src)                                                       │
   │                                                                                   ▼
   └─ kt-* sources copied here ───────────────────────────────────▶ packages/kt-*  ──Vite alias──▶ src (dev HMR)
                                                                                       │
                                          apps/<app>  ◀── consume dash-* (dist) + kt-* (source)
                                              │
                          dev:  esbuild transform per-module + optimizeDeps pre-bundle (CJS→ESM)
                          prod: Rollup bundle + tree-shake + code-split + esbuild minify
```

| Step | Tool | Output |
|---|---|---|
| Package transpile | tsup → esbuild | `dist/` mirrors `src/`, ESM |
| Type resolution | `typesVersions` → `src` | full-fidelity types, no `.d.ts` |
| Dev deps | Vite `optimizeDeps` (esbuild) | CJS→ESM, pre-bundled |
| Dev app/source | Vite + esbuild | per-module transform, HMR |
| Prod | Vite → Rollup + esbuild | tree-shaken, code-split, minified |
| CSS | Vite LESS pipeline | CSS custom properties |

## 10. Gotcha index (symptom → cause → §)

| Symptom | Cause | Fix |
|---|---|---|
| `does not provide an export named 'default'/'X'` (a CJS lib) | transitive CJS dep optimized without interop | add to `optimizeDeps.include` (§5) |
| `does not provide an export named 'X'` (a `dash-*` pkg) | stale **CJS** build in registry | rebuild + republish as ESM (§2) |
| `No known conditions for '.'` | object `exports` with only `import` | string exports (§3) |
| `React is not defined` (from a package) | classic JSX transform | `jsx:'automatic'` (§1) |
| `Could not resolve 'X'` | package imports an **undeclared** dep | declare it / app-level dep (§1) |
| duplicate package version in tree | `workspace:*` stamped an old version | `pnpm.overrides` to force one (§2) |
| `does not export X` from a single pkg's barrel | not re-exported in `src/index.ts` | add to barrel (§1) |
